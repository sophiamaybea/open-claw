# Self-Improvement & Lessons Learned

_Last updated: 2026-09-25_

### LEARN-001 — Implementation evidence outranks README wording
Inspect the code and tests behind a claimed capability before marking it WORKING.

### LEARN-002 — Self-improvement needs external evaluation
A model's own score is not evidence of better performance. Promote improvements only with tests, benchmarks, validators or real task outcomes.

### LEARN-003 — Persistent memory requires maintenance
Storage alone is not learning. Deduplication, supersession, links, confidence, failures and consolidation are required.

### LEARN-004 — Repository names are not sufficient identity
Before automated writes, verify repository purpose using metadata + recent commits + source.

### LEARN-005 — Revenue requires verified outcome states
Never add advertised rewards together as earnings. Track acceptance and payout evidence separately.

### LEARN-006 — Economic source provenance precedes scoring
A GitHub issue labelled bounty, paid or reward is not sufficient evidence of revenue. Classify the source as canonical payer/maintainer, official bounty platform, third-party mirror, agent-generated alert or unverified claim before scoring it. Verify payer, amount, claimability, acceptance criteria, payout route and payment precedent where practical.

### LEARN-007 — Merge acceptance and payment are separate outcome states
A merged PR proves code acceptance, not payment. Track merge/acceptance independently from payout verification, and penalise opportunities whose reward mechanics remain ambiguous.
